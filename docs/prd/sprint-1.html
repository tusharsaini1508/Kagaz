1What this sprint delivers

By Tuesday a customer can upload files, and each file is kept under that customer only. Every file is virus scanned before anything opens it, and stored once even if it is uploaded twice. Office files are turned into PDFs, phone photos into a standard image format, and a picture is saved of every page. If the file is a clean digital file (a normal PDF, Excel or CSV), its text is pulled out directly, with no AI, and stored in pieces that each know where they came from. A bare screen lists the files with their status and can open a page and draw a box on it. Nothing intelligent yet.

Why this matters later

Sprint 2 highlights the exact spot an answer came from, using the page pictures and positions stored now. If a position is missing or wrong now, no later sprint can point at the page.

2What this sprint deliberately does not deliver

  • Sprint 2Reading scanned pages and photos with AI. Sprint 2 D1, after Vrushit picks the scan reader (due Fri 25 Sep). Sprint 1 only marks what needs a reader (#19).
  • ProposalMasking Aadhaar and PAN, not in this sprint as planned. The plan puts it in Sprint 2 D1, but Sprint 1 already stores text. I propose moving it, see question 1.
  • Sprint 2Turning text pieces into searchable form, including meaning vectors in pgvector. Sprint 2 D2. Sprint 1 stores the pieces and nothing else.
  • Sprint 2Chat, answers, "not found", Hinglish questions.
  • Sprint 3Verified and needs review labels, the second reader, the correction screen where a reviewer sees both readings side by side and picks the right one, remembering corrections per customer. My own notes go further than the plan here, see question 16.
  • No sprintLogin is not in any sprint of the plan. #1 designs a users table and #35 needs a second customer account, but no task builds sign in. See question 3.
  • VrushitBuilt by Vrushit this sprint, not by me: cloud groundwork (#11, D2), the database with customer separation switched on (#12, D2), deployment to a test environment (#13, D3). I build on my own machine. Merged code deploys to the test environment.
  • NeverReading Hindi or Devanagari documents. Not ever at launch.

3How I will know it is done

The plan's gateFiles go in, text comes out of clean files, a picture exists of every page, and nothing leaks between customers.

In practice: fifty mixed files go through the pipeline with every failure explained and timings recorded (#24), the separation test passes on every pull request (#23), and Vrushit's four UAT checks pass (#33 to #36). What counts as a pass is question 7.

5Decisions I am making myself

  • The fingerprint is a SHA-256 hash of the file's bytes, from Python's standard library. No new dependency.
  • #21 comes before #20, and #22 is split into two pull requests: upload and file list early for #33, the viewer after #20. The day tags are the intended order, not a rule (CONTRIBUTING.md:43), and this keeps #20 behind the socket.
  • The retry count and how long a running job stays hidden are read from settings, never hard coded. The values are yours (section 6). I suggest 3 attempts.
  • Each pipeline step is its own small module under backend/, and each issue is its own pull request, under about 300 lines.
  • Tests ship with the code. Every pull request that adds customer owned data, or an endpoint or storage path that returns it, extends the isolation test and marks it isolation.
  • Customer messages say what happened and what to do next. Messages, stored failure reasons, log lines and failure bin entries carry an error code and ids only: never file contents, file names, parser error text or storage paths.
  • Automated tests use small synthetic files I make, or that the test generates (such as the hundred page PDF), committed with the tests, each under 2MB, with no real or real looking identity numbers. samples/, which git ignores, is only for my manual runs. No real document goes into the repo.
  • The screens are bare but usable: plain HTML controls, a labelled file input (no drag and drop needed), status as a word and not only a colour, loading, empty and error states said in words, usable by keyboard. No new library for this.

    Masking Never cut

    Sprint 1 stores text (#19, #20) but masking is Sprint 2 D1. Real invoices in #33 print GSTINs, which contain the full PAN, so real documents would put full PANs into stored text, raw reader output, file names, and possibly logs. Options: (A) move the masking task ahead of #20, about 2 more half days (a guess) on an already full sprint; (B) no text from real documents is stored until masking lands, so #33 and #36 run on real files and #34 on synthetic ones; (C) a written, dated exception from you. Either way, does masking also cover raw reader output and file names?

    I recommend A, because masking is on the never cut list.

    #1, #2 and #3 are not in docs/ yet. When do they land? None of my issues carry the needs-plan label, but the tasks marked DB in section 4 touch the database or separation. Which need a plan comment first?

    No sprint builds login. How does the upload endpoint know which customer is uploading? #35 edits ids in the request and must fail, so the stand in has to be something the server checks, not a customer id the client sends. Where do #33 to #36 run, my machine or the #13 test environment? Who can reach that environment before login exists, and may it hold real documents?

  4. 4

    Where the virus scan runs

    Inside the upload request before the job is queued, or as the first step in the worker? Is fingerprinting allowed before the scan (it reads the bytes, it does not open the file)? Until the scan passes, and after it fails, where is the file kept, for how long, and can anything ever serve it?

  5. 5

    Read endpoints for #22

    The file list and the viewer need the backend to list a customer's files and return a page. No issue names these endpoints. Are they part of #22, or a new issue?   6. 6

    Coordinates

    Does the viewer draw on the PDF through PDF.js or on the #18 page picture? Does a piece keep one box, or a box per line (and per word)? And the stand in reader in #21 wraps #19's output, right?

    Is a PDF judged per page or per document? Some PDFs mix text pages and scanned pages, and scanners often add a hidden text layer. For #33, does a scanned sample that is stored, pictured and marked as needing a reader count as "processed without a manual fix"? Does #24 need all fifty to pass, or are explained failures fine?

    My suggestion: per page, and a page that needs a reader gets its own status, not a failure.

The plan says checked at every layer, #23 says API and database: does it cover file storage too, so B cannot fetch A's page picture? In CI, are S3, SQS and the scanner real local services or fakes?
